# 支払い明細から探す 設計

## 暫定正本｜2026-09-01

> 本書は `SeiZen_全体設計.md` の下位文書とする。
> 記述が矛盾する場合は全体設計を優先する。
> 本書は設計書であり、実装指示書ではない。実装指示は本書から別途派生させる。

---

# 1\. 位置づけ

「支払い明細から探す」は、口座・カード等の過去明細から、現在整理対象となり得る契約を発見し、`契約・デジタル`へ登録する機能とする。

以下は目的にしない。

- 家計簿
- 支出分析
- 継続同期
- 継続監視

「サービスから探す」と並列の入口であり、いずれかが主ではない（§4-1、§7）。

---

# 2\. 成立させる状態

**選択した支払い手段から継続的に出ている支払いが、契約・デジタルに漏れなく載っている状態。**

成立の単位は支払い手段ごととする。銀行口座を処理すれば銀行口座の分が、カードを処理すればカードの分が成立する。

成立させるのは網羅であり、理解ではない。各契約の内容理解と対応の整理は、契約ごとの成果物UI上で進む（§4-1）。

登録件数は進捗ではない（§12）。

---

# 3\. 基本原則

## 3-1. 明細は判定対象ではなく、マスタへの接続キーとする

明細が確定できる事実は1種類のみとする。

**この期間に、この請求名義で、この金額の支払いがN回あった。**

サービス名・契約性・domain・対応時期・手続き方法は、いずれも明細に存在しない。これらはSeiZen側が持つ外部知識から供給する（§9）。

したがって明細側に、契約性やdomainを判定するロジックを置かない。周期・金額は判定基準ではなく、**マスタ内で絞り込むためのキー**として使う。

## 3-2. 登録エントリは「明細 ∪ マスタ」で埋める

| 供給元 | 項目 |
|---|---|
| 明細 | 金額 / 周期 / 初回出現日 / 最終出現日 |
| 支払い手段の登録情報 | 支払い手段 / 契約者名義 |
| マスタ | サービス名 / domain / 対応時期 / 確認項目 / 手続き方法 / 参考リンク |
| ユーザー | 接続できなかった場合のみ、名前と対応時期 |

契約者名義は明細に存在しない。画面3で選択した口座・カードの登録情報から決まる。誰の契約として登録されるかもここで決まるため、この機能で家族の指定を問わない。

明細が持たない項目を「持てない」として扱わない。マスタが持つ。

---

# 4\. 処理単位

処理単位は**支払い系列**とする。請求主体を単位にしない。

系列 = 同一請求主体のうち、周期と金額帯が揃うまとまり。

1つの請求主体が複数の系列に分かれる。

```
APPLE.COM/BILL
├ ¥150 × 毎月18日 × 6回     → 系列1
├ ¥1,200 × 1回（04/11）      → 系列2
└ ¥650 × 1回（08/22）        → 系列3
```

請求主体を単位にすると、金額と周期という絞り込みキーが失われ、本来確定できるものまでユーザーに問うことになる。上記の場合、系列1は金額から iCloud+（50GB プラン）に確定でき、系列2・3はどの料金型にも当たらないため候補にならない。

逆方向の統合（複数の請求主体が1契約に属する場合）は、この機能では扱わない。登録後に行う。

# 5\. 全体フロー

```
明細を読む
↓
① 正規化
↓
② 請求主体の同定
↓
③ 系列化
↓
④ 判定（§7）
↓
⑤ 既登録との照合
↓
⑥ ユーザー確認（確定できなかった箇所のみ）
↓
⑦ 契約・デジタルへ登録
↓
この支払い手段は確認済み
```

①〜③は明細側の処理として仕様を固定する。以後の可変部分はマスタ側に置く。

# 6\. 明細側の処理

## 6-1. 正規化

**使用する項目は「利用日」と「利用金額」とする。締め日・請求月・今回のお支払い金額は使わない。**

請求月・締め日ベースで系列化すると、分割払いが定額サブスクと同型になる。

| （請求月） | 利用日 | 店名 | 利用金額 | 支払区分 | 今回回数 | お支払い金額 |
|---|---|---|---|---|---|---|
| 2026-04 | 2026/04/05 | BIC CAMERA | 66,000 | 3 | 1 | 22,000 |
| 2026-05 | 2026/04/05 | BIC CAMERA | 66,000 | 3 | 2 | 22,000 |
| 2026-06 | 2026/04/05 | BIC CAMERA | 66,000 | 3 | 3 | 22,000 |

利用日・利用金額で見れば同一取引1件に畳まれる（利用日が同じ＝1回の買い物）。

このケース自体は請求主体（BIC CAMERA）の段階で落ちるが、マスタ未収録の請求主体で分割払いが使われた場合に影響するため、項目の指定を仕様とする。補助的に `支払区分 ≠ 1`（分割・リボ）を除外する。

返金行（負数、備考「返品」等）を除外する。

銀行明細を扱う場合、**出金行のみを対象とする**。入金行（年金・給与等）は毎月固定額として継続性を満たすが、契約ではない。

### 明細に無い項目

**「請求月」は実際の明細CSVには列として存在しない。** カード会社の明細は利用日を持つだけで、締め日・請求月は列にならない（三井住友カード / 楽天カード / セゾン / 三菱UFJ 等で確認）。対象期間（この支払い手段の明細をどこからどこまで見たか、§13 の確認済み記録に使う）は、**取り込んだ取引の利用日の最小〜最大**から導く。明細ファイルの見出し（対象期間の記載）があればそれを優先してよいが、無くても利用日から導けるので必須にしない。

## 6-2. 請求主体の同定

明細文字列から請求主体を同定する。表記揺れは列挙不能のため、固定ルール表では持たない（§12-1）。

## 6-3. 系列化

同一請求主体の取引を、間隔と金額帯で系列に分割する。

| 区分 | 間隔の目安 |
|---|---|
| 毎週 | 7日前後 |
| 毎月 | 28〜33日 |
| 隔月 | 56〜66日 |
| 単発 | 反復なし |

金額は固定・変動のいずれもあり得る。金額の一定性は系列化の条件にしない。

# 7\. 判定

判定は単一の木とする。周期・金額を単独のゲートとして先に置かない。

```
系列
└ 請求主体をマスタ照合
    ├ マスタにある
    │   ├ 支払い手段型              → §8-1 アップロード誘導
    │   ├ domain が対象外           → 出さない（§8-2）
    │   └ 系列の形を配下サービスの料金型と照合
    │        ├ 一致する             → 候補。金額でプランを絞る
    │        │    ├ サービスが一意  → A 確定
    │        │    └ 複数残る        → B サービス名を選ばせる
    │        └ 一致しない           → 出さない
    └ マスタにない
        ├ 継続性あり                → C 名前と対応時期を入力させる
        └ 継続性なし                → 出さない
```

## 7-1. 照合は2段階に分ける

| 段階 | 照合対象 | 決まること |
|---|---|---|
| ① 形 | 系列の周期・定額性 × 料金型 | 候補になるか |
| ② 金額 | 系列の金額 × プランの金額 | プランまで確定するか |

金額を照合キーにするかどうかは料金型が決める。

| 料金型 | 金額で照合するか |
|---|---|
| 定額（月額・年額） | する |
| 従量（電気・ガス・水道・携帯） | しない |
| 定期宅配 | しない |

全体に適用する許容幅を持たない。

金額が既知のプランと一致しない場合、**プランが確定しないだけで候補からは落とさない**。旧価格のまま契約しているケース（Netflix ¥1,490 等）を取りこぼさないため。この場合サービスは確定し、プランは未確定のまま登録する。

## 7-2. 「小売」「都度」という分類を持たない

配下に継続課金のサービスを持たない請求主体は、料金型との照合で自動的に落ちる。分類を人が付ける必要はない。

| 請求主体 | 配下の料金型 | 系列 | 結果 |
|---|---|---|---|
| BIC CAMERA | なし | ¥66,000 単発 | 形が一致しない → 出さない |
| SEIYU | なし | 変動・不規則 | 形が一致しない → 出さない |
| Amazon | Prime 年額 / Kindle Unlimited 月額 | 変動・不規則 18件 | 形が一致しない → 出さない |
| Apple | iCloud+ 月額 / Apple Music 月額 ほか | ¥1,200 単発 | 形が一致しない → 出さない |
| Apple | 同上 | ¥150 毎月 | 形が一致 → 金額で iCloud+ 50GB に確定 → A |
| Netflix | 月額 890 / 1,590 / 1,980 | ¥1,590 毎月 | 形が一致 → プランも確定 → A |
| Netflix | 同上 | ¥1,490 毎月 | 形が一致 → プラン未確定のまま A |
| Microsoft | Microsoft 365 年額 21,300 ほか | ¥21,300 単発 | 形が一致 → 確定 → A |
| 東京ガス | 従量・月次 | 変動・毎月 | 形が一致（金額は照合しない）→ A |

Amazonのように継続課金と都度購入が同一請求主体に混在する場合も、系列単位で照合するため分離される。

## 7-3. 年額・隔月の扱い

明細の期間が短い場合、年額契約は窓内で反復しない。これは例外ではなく、**料金型が年額であれば単発の出現が正しい形である**という7-1の帰結として処理される。反復の観測を要しない。

`MICROSOFT*MICROSOFT 365 ¥21,300 単発`、`GMO*ONAMAE.COM ¥1,408 単発` はいずれもこの経路でAになる。

明細の期間はユーザーが持ち込むものであり、こちらで制御できない。仕様上の期間下限は設けない。

## 7-4. 継続性の判定はCの経路にのみ適用する

マスタにない請求主体は、料金型との照合ができない。判定材料が反復しかないため、この場合に限り継続性で判定する。カテゴリレベルのマスタは持たない。名前と対応時期をユーザーが入力する経路が既にあり、その手前に分類を挟む理由がないため。

閾値は緩く取る。

- 誤って候補に出す → 画面上に出るためユーザーが外せる
- 候補に出さず落とす → 存在に気づけない

日常消費は間隔が不規則なため、実データ上は分離できる。

| | 間隔（日） |
|---|---|
| 日経新聞（契約） | 32, 28, 33, 28, 32 |
| SEIYU（消費） | 0, 6, 7, 34, 1, 40, 13, 15, 12, 10, 18 |
| TIMES PARKING（都度駐車） | 4, 60, 19, 24, 15, 14, 14, 12 |

## 7-5. 限界

**マスタにない請求主体の年額契約は、明細から発見できない。** 料金型との照合ができず、反復も観測されないため、いずれの経路も通らない。

これはこの機能の構造的な限界であり、「サービスから探す」側で補う。

# 8\. 特別扱いする2つの型

## 8-1. 支払い手段

カード会社・キャリア決済等への引き落としは、配下に継続サービスを持たない。7-1でも落ちるが、「マスタにない」としてCに混入すると誤った候補になるため、**マスタに `payment_method` 型として保持し、判定木で候補から除く**。明示的な型として持つ。不作為による除外にしない。

銀行口座とカードは階層ではなく並列の入口とする。銀行明細からカードの配下契約は判別できない（金額の合計しか現れない）。それぞれ別の入口としてアップロードすることを想定するが、**この画面から個別に誘導はしない**。検出した旨も表示しない（§12-2：提示しなかった支払いの内訳・判定理由は画面に出さない）。どの支払い手段をアップロードするかはユーザーが入口の一覧で判断する。

## 8-2. 他領域に属するもの

保険等、`契約・デジタル`以外の領域が扱う契約は、この機能では登録しない。

マスタに保持しないと「マスタにない」としてCに混入するため、**マスタに保持したうえで提示対象から外す**。不作為による除外にしない。

検出した旨も表示しない。契約・デジタルの網羅がこの機能の責任範囲であり、他領域の網羅はその領域が負う（§2）。

# 9\. マスタ接続の結果

| 結果 | 例 | 扱い |
|---|---|---|
| A 一意に確定 | NETFLIX.COM ¥1,590 毎月 → Netflix / APPLE.COM/BILL ¥150 毎月 → iCloud+（50GB プランと判定） | 確定 |
| B 候補が複数 | APPLE.COM/BILL 毎月・どのプラン額にも当たらない → iCloud+ / Apple Music / … | サービス名を選ばせる |
| C マスタにない | 継続性が認められる未知の請求主体 | 名前と対応時期を入力させる |

確信度・推測といった中間状態を持たない。絞れたら確定、絞れなければ選択、の2値とする。

Cのdomainは`契約・デジタル`とする。この画面から登録される以上、他領域の判定材料がない。

## プランの扱い

プランはサービスの下位実体とする。

```
サービス（Netflix）
├ domain / 対応時期 / 手続き方法 / 参考リンク  … サービスが持つ
└ プラン
    ├ 広告つき      890
    ├ スタンダード  1,590
    └ プレミアム    1,980
```

プラン金額は②の照合キーであるためプラン単位で必要となる。一方、手続き方法等はプラン間で共通のため、プランごとに別サービス行にすると複製が生じる。

**プランは表示・照合の単位ではない。** エントリの表示名はサービス名のみとし（プラン名・容量を併記しない。過剰表示になる）、既登録との照合も `サービス + 支払い手段` で行う（同一サービスの別プランを同時契約するケースは実務上ない）。判定したプラン（plan_id）はエントリに記録として持つに留める。

プランが確定した後も、エントリの金額は**明細由来の実額**を使う。マスタのプラン金額で上書きしない。金額とプランは連動する（プラン＝容量と金額の対）が、値上げでマスタのプラン金額が動いてもエントリの実額は動かさない。

プランが確定しない場合（旧価格・従量・定期宅配）は、plan_id を null のまま登録する。サービスが確定していれば domain・対応時期・確認項目は決まるため、支障はない。

Bで「その他」が選ばれた場合は、請求主体名のみが確定した状態となる。対応時期が決まらないためCと同じ扱いとし、対応時期をユーザーに問う。

# 10\. 対応時期

## 10-1. 判定

対応時期は分類ラベルではなく、次の事実から決まる。

**本人の生前の行為なしに、遺族が事後に手続きを完了できるか。**

| 判定 | 対応時期 |
|---|---|
| 完了できる | そのとき |
| 完了できない | いまのうち |

制度の有無だけを軸にしない。Appleの故人アカウント管理連絡先、Googleのアカウント無効化管理ツールは制度として存在するが、本人が生前に指定しなければ機能しない。事後単独では完了できないため「いまのうち」とする。

## 10-2. 既定値

判定は非対称である。

- 「そのとき」…… 遺族向け承継・解約手続きの存在を確認できる
- 「いまのうち」…… 制度の不存在は確認できない

したがって、**遺族向け手続きの存在を確認できたものだけ「そのとき」とし、確認できないものはすべて「いまのうち」を既定値とする。**

不要に事前準備させる害より、事後対応できると誤って伝える害の方が大きい（§10）。

## 10-3. 確認項目の導出

対応時期の判定根拠が、そのまま確認項目になる。項目リストを別途定義しない。

| 対応時期 | 確認項目 |
|---|---|
| いまのうち | ログインID / パスワード、登録メールアドレス、認証端末、解約手順 |
| そのとき | 契約者番号、手続き窓口、書類のありか |

# 11\. 既登録との照合

判定でサービスが確定した時点で、既登録エントリと照合する。

- **A** … 提示前に照合する
- **B** … ユーザーが選択した時点で照合する
- **C** … マスタにないため照合対象としない

照合キーは `サービス + 支払い手段`。

| 状況 | 扱い |
|---|---|
| 同一サービス・同一支払い手段で既登録 | 「登録済み」として提示。チェック不可 |
| 同一サービス・異なる支払い手段 | §13-2 |

既登録を候補から除外して非表示にしない。明細に出ているものが画面に現れないと、網羅されたかどうかをユーザーが判断できない（§2）。

---

# 12\. ユーザー確認

## 12-1. 確認の条件

この画面で確認するのは、次の1条件のみとする。

**明細でもマスタでも埋まらない欄のうち、ユーザーが今答えられるもの。**

| 状態 | サービス名 | 対応時期 |
|---|---|---|
| A 確定 | マスタ | マスタ |
| B 候補が複数 | ユーザーが選ぶ | 選択後にマスタから確定 |
| C マスタにない | 請求主体名（編集可） | ユーザーが選ぶ |

Bで対応時期を問わない。マスタが答えを持っているものをユーザーに判断させない（§2）。

Cは「分からない」を選択肢に含める。「分からない」を選んだものは一覧の「振り分け前」に入る。

## 12-2. 提示

Bの行はユーザーが選択した時点でAと同じ状態になるため、グループを分けると作業中に行が別グループへ移動する。

並び順は金額降順とする。

```
□ Netflix          動画配信      ¥1,590 / 毎月        登録済み
□ Spotify          音楽          ¥1,080 / 毎月
□ iCloud+          クラウド保存  ¥150   / 毎月
□ Microsoft 365    ソフト        ¥21,300 / 年1回
□ Apple                          ¥980 / 毎月
     どのサービスの支払いですか
     ( iCloud+ )  ( Apple Music )  ( Apple One )  ( その他 )
□ NTTドコモ        携帯          ¥6,000前後 / 毎月
□ ○○○○                         ¥13,200 / 毎月
     名前      [ ○○○○                ]
     対応時期  ( いまのうち ) ( そのとき ) ( 分からない )
```

提示しなかった支払いの内訳・判定理由は表示しない。「継続していない支払いは表示していません」の一文に留める。

# 13\. 登録

## 13-1. エントリが持つもの

- 請求主体名 / サービス名（確定した場合）
- 支払い手段 / 契約者名義
- 金額 / 周期 / 初回出現日 / 最終出現日
- domain / 対応時期

確認項目・手続き方法・参考リンクはマスタから表示時に引く。エントリに複製しない。マスタ更新時にずれるため。

金額が変動する系列（`NTT DOCOMO 5,764〜6,425`、`東京ガス 3,552〜5,124`）は、**目安額として記録し、変動する旨を注記する**。単一値として断定しない。

接続できなかったエントリ（C）は、明細由来の項目とユーザー入力のみを持つ。これは未完成の記録ではなく、明細から取れる分を取り切った正常な出力とする。

## 13-2. 支払い手段が変わっている場合

同一人物が同一サービスを同時に2つの支払い手段で払う状況は通常発生しないため、これは支払い手段の変更として扱う。

既存エントリの支払い手段を上書きする。履歴を持たない。一覧の「支払いのつながり」は現在の経路が正しいことのみが要件であり、古い経路が残ると誤った警告になる。

期間が重複する稀なケースは、自動判定せず2件として登録する。

---

# 14\. 完了

未処理の候補が0件になった時点で、その支払い手段について完了とする。

「追加しない」と判断した系列は、`請求主体 + 金額 + 周期 + 支払い手段` を指紋として記録し、同じ支払い手段の別期間を再アップロードした際に再提示しない（§11の状態管理）。

ただしこの機能は継続監視を行わず、同じ支払い手段を再アップロードする頻度が低いため、**初回実装の対象外**とする。

---

# 15\. マスタ

## 15-1. 情報の置き場所

**再現性が要るものはデータで持つ。最新性が要るものは実行時に解決する。**

| 情報 | 種類 | 置き場所 | 理由 |
|---|---|---|---|
| 明細文字列 → 請求主体 | 事実・揺れが無限 | 実行時解決 | `SPOTIFY P0C8A7` 等の接尾辞は列挙不能 |
| 請求主体 → 配下サービス | 事実 | 実行時解決 | サービスは増減する |
| 料金型・プラン金額 | 事実・変化する | 実行時解決 | 値上げにより静かに陳腐化する |
| 死後手続き | 事実・変化する | 実行時解決＋保存 | 解約導線は変わる。古い手順は害が大きい |
| domain | SeiZenの分類 | データ | 実行ごとに変わってはならない |
| 支払い手段型・対象外指定 | SeiZenの判断 | データ | 同上 |

対応時期は死後手続きの調査結果から導出するため、独立した項目として持たない。両者が食い違う状態を構造的に作らない。

ただし調査結果は保存し、更新は意図的に行う。実行ごとに再判定すると、一覧のグループが日によって変わる。

## 15-2. 実行時解決の設計

- **呼び出し単位** … 明細行ごとではなく、系列化後の系列をまとめて1回。
- **送信範囲** … 請求主体名・金額・周期のみ。口座番号、名義、家族の識別情報を含めない。系列化を手元で完了させてから問い合わせることで、送信対象が構造的に絞られる。
- **結果の蓄積** … 解決結果は事実側の列のみマスタへ書き戻す。書き戻すのは請求主体とサービスの対応関係であり、家族の情報を含まない。画面上の「データは保存されません」と矛盾しない。同一請求主体は次回以降、問い合わせ不要になる。
- **失敗の向き** … 迷った場合は照合を試み、絞れなければBに落とす。

マスタは事前構築物ではなく、利用の結果として育つものとする。

## 15-3. 人が用意するもの

- カテゴリ × domain
- 支払い手段型の指定
- 対象外指定（保険等）

サービス単位の網羅入力を必要としない。「小売」「都度」の分類（§7-2）もカテゴリレベルのマスタ（§7-4）も持たない。

## 15-3b. マスタとユーザーデータの分離（永続化）

本番では：

- **マスタ**（契約カタログ・支払い手段マスタ・手続き情報・`domain`・支払い手段型など §15-1 の「データ」側）はサーバの DB。フロントは毎回 `GET` で取得し、コピーを永続化しない。マスタの更新（列の追加、文言の修正、`statement_format` の追加）は、次のリロードで自然に反映される。
- **ユーザーのデータ**（登録した契約、入力した対応方針・アカウント情報、明細の確認記録）もサーバの DB。`POST`/`PATCH` で書く。
- フロントの状態はキャッシュにすぎない。

プロトタイプでこれを写すときも、**seed（＝マスタ＋工場出荷データ）は永続化しない**。ローカルに保存するのは「本番でサーバに `POST` するもの」だけ：ユーザーが追加した契約、seed への編集を項目ごとに差分で、明細の確認記録、ユーザーが追加した支払い手段。ロード時は seed（コード）＋ 保存されたユーザーデータ（差分・追加分）で組み立てる。

seed の写しを丸ごと保存すると、コード側の seed を更新するたびに古い保存とぶつかり、リロードしても反映されない。この形なら seed のスキーマを変えても保存と衝突しない。

## 15-4. 明細形式への非依存

本設計はカード明細（三井住友カード Vpass 形式）で検証しているが、判定木は明細形式に依存しない。判定木に渡すのは正規化済みの取引配列（利用日 / 金額 / 店名）だけで、そこへ至る「CSV → 取引配列」の変換を **1つの汎用アダプタ**が担う。

銀行明細で摘要がカナ略記となる点は、`SPOTIFY P0C8A7` 等と同じ表記揺れであり、実行時解決の対象に含まれる。同定できなければCへ行くという経路が定義済みのため、未定義の挙動は生じない。

### 会社別アダプタは持たない

明細CSVの列名・列順・列数・文字コード・ヘッダー行の有無は、カード会社ごとに異なる（三井住友カードはヘッダー行なし・11列・先頭にカード情報行・末尾に合計行・Shift-JIS。楽天カードはヘッダー行あり・10列・UTF-8。セゾン・UC・三菱UFJ もそれぞれ別）。

しかし**必要な意味は3つだけ**：利用日・利用金額・利用店名。補助的に「一括払いか否か」（分割・リボの除外用）。会社ごとにアダプタを書くと、対応カードが増えるたびに実装が要り、ユーザーは「自分のカードは対応しているか」を気にすることになる。

代わりに、**CSVの中身から列の意味を推定する汎用アダプタ**（`payment/source/statement-csv.js`）1本で読む。支払い手段が形式を宣言する必要はない（`statement_format` は持たない）。

### 列の推定

1. **文字コード** … バイト列を UTF-8 として厳格デコード。不正バイトがあれば Shift-JIS(CP932) とみなす。BOM は除去。

2. **ヘッダー行の有無** … 先頭の非空行の各セルを見て、「日付でも数値でもないセル」が大半 → ヘッダー行。日付・数値が含まれる → ヘッダーなし。

3. **各列の役割** … 全データ行を走査し、列ごとに値の性質を集計：
   - **日付列** … `YYYY/M/D` 等の日付として解釈できる値の割合が最も高い列。複数あれば、ヘッダー名が「利用日／ご利用日／日付／ご利用年月日」等にマッチする方を優先。なお「請求月」「支払月」相当（`YYYY/MM` 形式・締め日）は日付列にしない。
   - **金額列** … 整数（カンマ・通貨記号を除いて数字のみ）の割合が高い列のうち、ヘッダー名が「利用金額／ご利用金額／利用額」にマッチする列。マッチが無ければ、日付列に隣接し値の桁が取引額らしい（数百〜数十万）列。「支払総額／今回支払／お支払い金額／手数料／残高」相当の列は避ける（分割で総額と乖離するため・§6-1）。
   - **店名列** … 日付列・金額列・明らかな区分列を除いた列のうち、値のバリエーションが最も大きい（＝ユニーク値の割合が高い）列。ヘッダー名「利用店名／ご利用店名／利用店名・商品名／ご利用内容」があれば優先。
   - **一括/分割の区分列**（任意）… 「1回払い／一括／リボ／分割／ボーナス」等のキーワード、または `1`／`2`以上の小整数を持つ列。見つかれば、一括以外の行を除外する。見つからなければ、金額列と「支払総額」相当列の乖離があれば分割とみなす。乖離判定もできなければ、分割の除外はしない（§7-1 で BIC CAMERA 型は請求主体の段階で落ちるため実害は小さい）。

4. **明細行の判定** … 日付列が日付として読める行だけを取引とする。日付列が空・非日付の行（カード情報行・小計/合計行・「現地利用額…」の補足行・空行）は黙ってスキップする。

5. **推定できないとき** … 日付列が特定できない、または取引を1件も取り出せない場合は「この CSV から明細を読み取れませんでした」と返す（黙って空を返さない）。列の意味が一意に決まらない曖昧なケースは、初回実装では「読み取れませんでした」に倒す。ユーザーに列を選ばせる確認画面は将来の拡張とする（§12「今答えられることだけ聞く」の範囲だが、初回スコープ外）。

### 使う項目・除外（再掲・§6-1）

利用日 → usage_date、利用金額 → amount（正の円）、利用店名 → merchant_raw / merchant_norm。
分割・リボ行を除外、負数・0を除外。対象期間は取引の利用日の最小〜最大から導く。
